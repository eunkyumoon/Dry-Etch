## 📝 테스트 케이스 작성 체계

### 테스트 케이스 명명 규칙

**형식:** `TC-F-XXX_[기능명].md`

**예시:**
- `TC-F-001_Vpp_Data_Collection.md`
- `TC-F-026_Degradation_Index_Calculation.md`
- `TC-F-043_Vpp_Surge_Detection.md`

### 테스트 케이스 템플릿 구조

각 테스트 케이스는 다음 항목을 포함합니다:

1. **테스트 케이스 기본 정보**
   - 테스트 ID
   - 기능 ID
   - 기능명
   - 우선순위
   - 테스트 유형
   - 테스트 환경
   - 예상 소요 시간

2. **테스트 목적**
   - 테스트의 목적 명시

3. **전제 조건 (Prerequisites)**
   - 테스트 실행 전 필요한 조건

4. **테스트 데이터**
   - 테스트에 사용할 데이터

5. **테스트 단계**
   - Step별 상세 절차
   - 예상 결과
   - 실제 결과
   - 통과 여부

6. **테스트 결과 요약**
   - 전체 테스트 상태
   - 통과/실패 통계

7. **실패 케이스 분석** (실패 시)
   - 실패 원인
   - 재현 절차
   - 해결 방안

### 테스트 케이스 작성 프로세스

```
1. 기능 선택
   ↓
2. 템플릿 복사
   ↓
3. 정보 입력
   ↓
4. 테스트 단계 작성
   ↓
5. 검토
   ↓
6. 승인
   ↓
7. 테스트 실행
```

## 🐛 버그 관리 체계

### 버그 리포트 템플릿

버그 발견 시 다음 정보를 포함하여 리포트를 작성합니다:

| 항목 | 설명 |
|------|------|
| **버그 ID** | BUG-XXX (고유 식별자) |
| **관련 기능** | F-XXX |
| **심각도** | Critical / High / Medium / Low |
| **우선순위** | P0 / P1 / P2 |
| **재현 절차** | 단계별 설명 |
| **예상 결과** | 예상되는 정상 동작 |
| **실제 결과** | 실제 발생한 동작 |
| **스크린샷/로그** | 파일 경로 |
| **환경 정보** | OS, 브라우저, 버전 등 |

### 버그 상태 관리

| 상태 | 설명 |
|------|------|
| **신규 (New)** | 새로 발견된 버그 |
| **할당됨 (Assigned)** | 담당자에게 할당됨 |
| **수정 중 (In Progress)** | 수정 진행 중 |
| **수정 완료 (Fixed)** | 수정 완료, 재테스트 대기 |
| **검증됨 (Verified)** | 재테스트 통과 |
| **종료됨 (Closed)** | 버그 해결 완료 |

### 버그 우선순위 기준

#### Critical (치명적)
- 시스템 다운
- 데이터 손실
- 보안 취약점

#### High (높음)
- 핵심 기능 동작 불가
- 심각한 성능 저하
- 데이터 오류

#### Medium (중간)
- 기능 일부 동작 불가
- 사용성 문제
- 경미한 성능 저하

#### Low (낮음)
- UI 개선 사항
- 문서 오류
- 경미한 버그

### 주요 지표 정의

| 지표 | 계산식 | 목표 |
|------|--------|------|

| **버그 해결율** | 해결된 버그 수 / 발견된 버그 수 | ≥ 95% |

- **주간 모니터링**: 테스트 실행률, 통과율
